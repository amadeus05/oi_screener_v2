# Pump Screener TODO

## Базовая гипотеза начала пампа

Наблюдаемые признаки:

1. Многократное увеличение торговых объемов.
2. Резкий рост Open Interest.
3. Сильная положительная дельта между рыночными покупками и продажами.

Источник гипотезы:

- Наблюдения из YouTube-материалов.

## Важное уточнение

Эти признаки нельзя считать уникальными индикаторами пампа.
Они также могут встречаться при:

- breakout после накопления;
- short squeeze;
- реакции на новость;
- входе крупного участника в направленное движение.

Поэтому в системе это должно называться не "детектор пампа", а детектор аномального направленного дисбаланса с дальнейшей фильтрацией.

## Базовые сигналы для первой версии скринера

### 1. Volume Spike

Идея:
Текущий объем за окно `N` минут сравнивается со средним объемом за историческое базовое окно.

Черновая метрика:

`volumeRatio = currentVolume / averageVolume`

### 2. Open Interest Spike

Идея:
Измерять резкое изменение OI за короткий интервал.

Черновые метрики:

- `oiChangePct`
- `oiChangeAbs`

### 3. Aggressive Delta

Идея:
Считать дисбаланс между агрессивными рыночными покупками и продажами.

Черновая метрика:

`deltaRatio = (marketBuys - marketSells) / totalTakerVolume`

### 4. Price Displacement

Идея:
Подтверждать, что дисбаланс реально двигает цену вверх.

Черновая метрика:

`priceChangePct`

### 5. Liquidity Filter

Идея:
Отсекать неликвидные инструменты и мусорные сигналы.

Примеры фильтров:

- минимальный 24h volume;
- минимальное количество сделок;
- минимальная глубина стакана.

### 6. Noise Filter

Идея:
Исключать одиночные всплески без продолжения.

Примеры:

- подтверждение на нескольких свечах;
- удержание цены после всплеска;
- отсутствие мгновенного возврата в диапазон.

## Интерпретация комбинаций

- Volume растет + OI растет + Delta положительная + Price растет:
  сильный кандидат на старт направленного движения вверх.
- Volume растет + Delta положительная + OI падает:
  вероятнее закрытие шортов или фиксация, а не новый набор позиции.
- OI растет + цена почти не двигается:
  возможен набор позиции перед движением, но не факт, что памп уже начался.

## Черновой rule-based trigger для MVP

```ts
type PumpSignalInput = {
  volumeRatio: number;
  oiChangePct: number;
  deltaRatio: number;
  priceChangePct: number;
};

function isPumpStartSignal(input: PumpSignalInput): boolean {
  return (
    input.volumeRatio >= 3 &&
    input.oiChangePct >= 5 &&
    input.deltaRatio >= 0.2 &&
    input.priceChangePct >= 1.5
  );
}
```

Для production-логики предпочтительнее использовать не `boolean`, а score-based подход.

Пример направления:

```ts
  deltaScore * 0.20 +
  priceScore * 0.15;
```

## Уточненные функциональные требования

### Параметры правила

Каждое правило должно быть конфигурируемым и включать как минимум:

1. Минимальный процент роста OI.
2. Максимальный интервал в минутах, в пределах которого этот рост OI должен произойти.
3. Cooldown между повторными сигналами по одной и той же монете.

Пример смысла правила:

- если OI вырос не менее чем на `X%`
- в любой момент внутри диапазона последних `Y` минут
- и по монете не было сигнала в течение `cooldownMinutes`
- тогда можно формировать новый сигнал при выполнении остальных условий.

Важное уточнение:

- если в правиле указано `30` минут, это не означает, что рост должен формироваться ровно 30 минут;
- если нужный рост OI произошел за `5` минут внутри диапазона последних `30` минут, это тоже считается валидным сигналом;
- то есть правило задает верхнюю границу lookback-окна, а не фиксированную длительность события.

### Нумерация сигналов

Сигналы по каждой монете должны нумероваться в пределах суток.

Пример:

- `BTCUSDT #1`
- `BTCUSDT #2`
- `BTCUSDT #3`

Это означает, что системе нужен суточный счетчик сигналов отдельно по каждому инструменту.

### Несколько правил одновременно

Пользователь может задать `N` правил.

Требование к обработке:

- все правила активны одновременно;
- каждое правило проверяется независимо;
- одна и та же 1-minute candle должна прогоняться через весь набор правил.

### Таймфрейм проверки

Все правила проверяются на 1-minute candles.

Важно:

- даже если правило анализирует окно `X` минут, базовой единицей обработки остается 1-minute candle;
- значит, система должна уметь на каждой новой минутной свече пересчитывать метрики на lookback-окне правила;
- при этом проверка должна находить рост OI на заданный процент в любом подинтервале от `1` до `X` минут внутри lookback-окна.

## Следствия для архитектуры

Из этих требований следует, что в системе понадобятся:

- сущность правила со своими параметрами;
- движок, который на каждой 1-minute candle запускает проверку всех активных правил;
- хранилище/сервис cooldown по монете и правилу;
- хранилище/сервис суточной нумерации сигналов по монете;
- модель сигнала, которая хранит номер сигнала за сутки, правило-источник и timestamp.
- алгоритм поиска минимального/подходящего подинтервала, в котором OI достиг нужного процента роста внутри lookback-диапазона.
- абстракция биржи, через которую движок получает все рыночные данные.

## Логика проверки OI growth

На каждой новой 1-minute candle система должна:

1. взять последние `oiGrowthMaxWindowMinutes` значений OI;
2. проверить, существует ли внутри этого диапазона хотя бы один подинтервал, в котором рост OI достиг `oiGrowthPercent`;
3. если такой подинтервал найден, считать условие по OI выполненным.

Пример:

- правило: рост OI не менее `10%` за период до `30` минут;
- фактически OI вырос на `10%` за `5` минут;
- результат: условие считается выполненным, сигнал разрешен.

## Решение по интеграции с биржами

На текущем этапе система работает без агрегации данных между биржами.

Принцип:

- каждая биржа рассматривается как отдельный источник данных;
- rules engine работает с данными одной конкретной биржи;
- для подключения новой биржи реализуется единый интерфейс адаптера.

Это позволит:

- не смешивать несовпадающие OI/volume/delta между площадками;
- сохранить чистую архитектуру;
- позже без перелома доменной логики добавить агрегатор поверх exchange adapters.

### Уточнение по режиму работы

Система не подтягивает исторические данные с биржи.

Принцип работы:

- бот стартует и начинает собирать данные в реальном времени;
- бот хранит и агрегирует данные в локальном окне;
- сигналы запрещены, пока окно не прогрето до нужной глубины;
- все метрики считаются только на основе накопленных realtime-данных.

Базовая настройка:

- окно локальной агрегации: `60` минут;
- это значение должно быть вынесено в конфиг;
- максимальное окно правила, например рост OI за `30` минут, не должно превышать глубину локально накопленных данных.

Следствие:

- если бот только что стартовал и накопил менее нужного окна, сигналы не отправляются;
- warmup считается обязательной частью жизненного цикла скринера.

## Exchange Interface

Нужен контракт биржи, который описывает методы realtime-получения всех данных, необходимых для расчета сигналов.

Черновой вариант:

```ts
export enum ExchangeId {
  BINANCE = 'BINANCE',
  BYBIT = 'BYBIT',
  OKX = 'OKX',
}

export type MarketCandle = {
  symbol: string;
  openTime: Date;
  closeTime: Date;
  open: number;
  high: number;
  low: number;
  close: number;
  volume: number;
};

export type OpenInterestPoint = {
  symbol: string;
  timestamp: Date;
  openInterest: number;
};

export type AggressiveTradeStats = {
  symbol: string;
  timestamp: Date;
  marketBuyVolume: number;
  marketSellVolume: number;
  totalTakerVolume: number;
};

export interface ExchangeMarketDataProvider {
  getExchangeId(): ExchangeId;

  getSupportedSymbols(): Promise<string[]>;

  subscribeTo1mCandles(
    symbols: string[],
    onCandle: (candle: MarketCandle) => Promise<void> | void,
  ): Promise<MarketSubscription>;

  subscribeToOpenInterest(
    symbols: string[],
    onOpenInterestPoint: (point: OpenInterestPoint) => Promise<void> | void,
  ): Promise<MarketSubscription>;

  subscribeToTrades(
    symbols: string[],
    onTrade: (trade: MarketTrade) => Promise<void> | void,
  ): Promise<MarketSubscription>;
}
```

## Назначение методов интерфейса

- `getSupportedSymbols()`:
  список инструментов, которые можно сканировать на конкретной бирже.
- `subscribeTo1mCandles()`:
  поток минутных свечей для расчета volume/price signals.
- `subscribeToOpenInterest()`:
  поток точек OI для накопления локальной истории и поиска роста на нужный процент.
- `subscribeToTrades()`:
  поток трейдов для построения локальной дельты market buy / market sell.

## Архитектурная идея

Доменная логика не должна знать детали REST/WebSocket API конкретной биржи.

Правильное разделение ответственности:

- `ExchangeMarketDataProvider`:
  контракт источника данных;
- `BinanceMarketDataProvider`, `BybitMarketDataProvider`:
  конкретные адаптеры;
- `PumpRuleEvaluationEngine`:
  использует интерфейс и не зависит от реализации биржи.

## Warmup и локальная агрегация

Нужен отдельный буфер/агрегатор в приложении:

- хранит последние `aggregationWindowMinutes` данных по каждой монете;
- отбрасывает старые записи;
- считает готовность инструмента к сигналам;
- отдает rules engine уже накопленные локальные метрики.

Черновые правила готовности:

- если накоплено меньше `warmupMinutes`, инструмент не проверяется на сигнал;
- если правило требует окно `30` минут, а в буфере есть только `18` минут, правило не выполняется и не фейлится, а считается `not ready`.
